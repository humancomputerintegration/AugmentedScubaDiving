# C#과 Unity를 처음 읽는 순서

이 안내서는 최종 프로젝트의 실제 소스를 기준으로 구성요소를 연결합니다. 각 C# 파일의 의미 있는 줄에는 한국어 설명이 있습니다. 여기서는 그 줄들을 읽기 전에 **누가 어떤 일을 하는지, 값이 어디서 어디로 가는지**를 먼저 정리합니다.

## 1. Scene은 무대, GameObject는 물체, Component는 역할

`Simulation.unity`는 이번 시뮬레이션의 Scene입니다. Scene은 물체의 배치와 서로 연결된 참조를 저장합니다. `GameObject`는 이름을 가진 물체이고, `Component`는 그 물체에 붙인 기능입니다. 같은 손목 버튼도 화면에 그리는 기능, 닿았는지 알아내는 기능, 클릭 후 통화를 여는 기능이 필요합니다.

| 구성요소 | 손목 버튼에서 하는 일 |
|---|---|
| RectTransform | 버튼의 위치·폭·높이를 저장한다. |
| Image 또는 CircleGraphic | 배경과 원형 모양을 그린다. |
| Text | CALL처럼 읽을 글자를 그린다. |
| BoxCollider | 손끝 구 또는 레이저가 닿았는지 검사할 공간을 만든다. |
| Button | 실행할 함수 목록인 onClick을 가지고 있다. |
| HandUIButton | 어느 손으로 누를 수 있는지와 연속 클릭 간격을 확인한다. |

`HandUIInteractor`는 각 버튼에 따로 붙어 있지 않습니다. 시스템에서 양손을 읽고 누를 버튼 하나를 찾는 담당자입니다. `HandUIAnchor`는 메뉴 전체가 팔이나 손목을 따라가게 합니다. 그 결과, 화면 메뉴와 팔 메뉴가 서로 다른 위치에 있어도 같은 통화 함수를 호출할 수 있습니다.

Inspector의 참조 칸은 다른 물체의 **주소**를 저장한다고 생각하면 됩니다. 변수가 `Transform head`라면 숫자 자체가 아니라 머리 Transform을 가리킵니다. 코드가 `head.position`을 읽을 때 그 순간의 실제 머리 위치를 가져옵니다. `.meta`의 GUID와 Scene의 fileID는 Unity가 이러한 연결을 복원할 때 쓰는 식별자이므로 파일을 복사할 때 함께 보존해야 합니다.

## 2. 먼저 익힐 C# 문법

| 실제 문법 | 뜻 |
|---|---|
| `class HandsInput : MonoBehaviour` | HandsInput이라는 기능 묶음을 만들고 Unity의 생명주기 호출을 받는다. |
| `float speed = 2.4f;` | 소수 값 하나를 저장한다. 여기서는 초당 2.4미터라는 의미를 부여했다. |
| `bool underwater` | 참 또는 거짓만 저장한다. |
| `Vector3` | x·y·z 숫자 세 개다. 위치·방향·속도로 쓸 수 있으므로 문맥과 단위를 함께 읽는다. |
| `[SerializeField]` | private 변수도 Unity가 Inspector 값으로 저장·복원할 수 있게 한다. |
| `public` / `private` | 다른 코드에서 접근할 수 있는 범위를 정한다. |
| `if (조건)` | 조건이 참일 때 아래 문장 또는 중괄호 범위를 실행한다. |
| `return` | 함수 실행을 여기서 끝낸다. 반환값이 있는 함수라면 값을 함께 돌려준다. |
| `&&` / `!` | 둘 다 참 / 참과 거짓 뒤집기. |
| `==` / `=` | 같은 값인지 비교 / 오른쪽 값을 왼쪽에 저장. |
| `object.Method()` | object가 가진 함수를 호출한다. |
| `{ ... }` | 클래스·함수·조건문에 속하는 범위를 묶는다. |
| `// 설명` | 실행하지 않는 주석이다. |

이름은 물리 법칙을 자동으로 만들지 않습니다. `speed`라는 이름을 써도 C#은 단위를 모릅니다. 속도에 시간을 곱해서 거리를 만드는 책임은 코드를 작성하는 사람에게 있습니다.

## 3. 한 프레임이 지나가는 순서

프레임은 화면을 한 번 갱신하는 과정입니다. 이 프로젝트는 서로 의존하는 입력·배치·이동의 순서를 `DefaultExecutionOrder`로 정했습니다. 작은 값부터 Update를 실행합니다.

| 순서 | 실제 파일 | 읽는 것 | 만드는 것 |
|---:|---|---|---|
| -100 | HandsInput.cs | XR 손 관절과 추적 상태 | 왼손 주먹, 오른손 엄지 방향, 처음 쥔 순간, 손끝·레이 |
| -95 | HandUIAnchor.cs | 손목·손바닥 위치와 머리 | 팔·손목·손등 UI 위치 |
| -94 | WaveMenuController.cs | 왼손 스와이프와 메뉴 상태 | 화면 메뉴와 열린 패널의 위치 |
| -90 | HandUIInteractor.cs | 현재 손끝·레이·버튼 충돌 영역 | 클릭 1회, 강조 표시, 해당 손의 UIBusy |
| 0 | SimpleMovement.cs | 손 동작과 UIBusy, 카메라 방향 | 합친 이동 벡터와 CharacterController.Move 한 번 |

`Awake`에서는 필수 연결을 준비합니다. `Start`는 초기 설정에 사용합니다. `Update`는 프레임마다 입력·표시·이동을 갱신합니다. `LateUpdate`는 그 프레임의 Update 뒤에 머리를 따라가는 화면 등을 맞춥니다. `OnDisable`은 컴포넌트가 꺼질 때 남은 강조 표시나 추적 설정을 정리합니다.

모든 Update의 순서가 자동으로 보장되는 것은 아닙니다. 그래서 꼭 먼저 필요한 입력과 UI 판정에 순서를 명시했습니다. 실제 손 추적·렌더링 타이밍은 Unity와 Quest에서도 검사해야 합니다.

## 4. 예제 1 — 레이저로 CALL을 누를 때

아래는 코드 경로를 설명하는 **예시 실행 추적**입니다. Quest에서 관찰한 로그를 가장한 기록이 아닙니다.

| 단계 | 입력·조건 | 처리 | 결과 |
|---|---|---|---|
| 1 | 손을 편 상태에서 CALL을 가리킨다. | HandsInput이 현재 레이를 만들고 HandUIInteractor가 가장 앞의 UI를 찾는다. | CALL이 강조된다. 아직 클릭하지 않는다. |
| 2 | 같은 버튼을 가리킨 채 손을 쥔다. | 이번 프레임의 FistPressedThisFrame이 참이다. | 선택을 요청한다. |
| 3 | 허용된 손이고 버튼이 활성이다. | HandUIButton.CanUse가 통과하고 Press가 연속 클릭 시간을 검사한다. | 다음 허용 시각을 먼저 저장한다. |
| 4 | 클릭이 허용됐다. | Button.onClick.Invoke가 Inspector의 연결 함수를 호출한다. | CALL 메뉴가 열린다. |
| 5 | 선택한 손이 계속 주먹이다. | UI 선택 중이라는 기억을 유지한다. | 왼손이면 전진 명령에 동시에 쓰지 않는다. |
| 6 | 손을 편다. | 선택 유지 상태를 해제한다. | 다음번 새 주먹 동작을 받을 수 있다. |

**“주먹인 상태”와 “방금 주먹이 된 순간”은 다릅니다.** 이동은 쥐고 있는 동안 이어져야 하지만 클릭은 한 번만 실행되어야 합니다. 그래서 `LeftFist`와 `LeftFistPressedThisFrame`처럼 서로 다른 신호가 필요합니다.

직접 터치는 검지 끝을 작은 구로 보고 버튼 Collider와 겹치는지 확인합니다. 손을 조금 떨었다고 같은 버튼이 계속 재입력되지 않도록, 떼었다고 판단하는 거리에 여유를 둡니다. 새 추적이 시작된 순간에는 손이 이미 버튼 안에 있어도 클릭하지 않고, 한 번 빠져나왔다가 다시 들어오게 합니다.

읽을 파일: `HandsInput.cs` → `HandUIButton.cs` → `HandUIInteractor.cs` → `WaveMenuController.cs`.

## 5. 예제 2 — 앞으로 가며 위로 수영할 때

`SimpleMovement.Update()`는 프레임마다 속도를 0에서 시작합니다. 이전 프레임의 이동 명령을 쌓아 두지 않아 손을 놓으면 관성처럼 남지 않습니다.

왼손 주먹은 `xrCamera.forward * speed`를 만듭니다. `forward`는 카메라가 보는 방향의 길이 1 벡터입니다. 카메라가 아래를 보면 아래 성분도 포함합니다. 오른손 엄지는 `-1`, `0`, `+1` 가운데 하나를 줍니다. 물속일 때만 이를 세계의 위 방향인 `Vector3.up`에 곱해 합칩니다.

예를 들어 정면이 `(0, 0, 1)`, 전진 속도가 2.4m/s, 엄지 상승 속도가 1m/s이면 다음과 같습니다.

| 계산 | 값 | 의미 |
|---|---|---|
| 왼손 전진 | `(0, 0, 2.4)` m/s | 초당 z 방향 2.4m |
| 오른손 상승 | `(0, 1, 0)` m/s | 초당 y 방향 1m |
| 두 명령 합 | `(0, 1, 2.4)` m/s | 전진과 상승을 동시에 요청 |
| 길이 | `sqrt(1² + 2.4²) = 2.6` m/s | 그냥 더하면 대각선 속도가 증가 |
| 최고 속도 제한 뒤 | 약 `(0, 0.923, 2.215)` m/s | 방향 비율을 유지하며 전체 속도를 2.4로 제한 |
| 프레임 시간이 0.02초일 때 | 약 `(0, 0.0185, 0.0443)` m | 이번 프레임에 요청할 이동 거리 |

이 거리를 `CharacterController.Move`에 **한 번** 전달합니다. 충돌이 있으면 실제 이동 거리는 요청보다 작을 수 있습니다. 물리 결과와 요청 벡터를 구별해야 합니다.

두 스크립트가 각각 위·아래와 앞 이동을 하면 실행 순서·충돌·중력 때문에 결과가 달라질 수 있습니다. 최종 Scene에서는 기존 별도 엄지·stroke·Mud 이동 담당을 비활성화하고, 이동 명령을 이 함수에 모았습니다. Rigidbody도 중력으로 따로 떨어뜨리지 않도록 구성했습니다.

읽을 파일: `SimpleMovement.cs`. 손 모양 판정의 비율과 유효 관절 조건은 `HandsInput.cs`, 수면 높이 기준은 `InformationManager.cs`에서 확인합니다.

## 6. 예제 3 — 배터리와 수심을 표시할 때

계산의 원본은 `InformationManager`, 보이는 글자와 색은 `DiveStatusHUD`가 담당합니다. 둘이 각각 다른 배터리를 계산하면 화면마다 숫자가 달라질 수 있으므로 HUD는 원본을 읽습니다.

원본 `GetDepth()`는 이름과 달리 `머리 y - 수면 y`를 반환합니다. 수면이 13m이고 머리가 8m라면 결과는 -5m입니다. HUD는 사용자가 읽을 양의 수심을 만들기 위해 `Max(0, -signedHeight)`를 계산하여 **DEPTH 5.0m**로 보여 줍니다.

배터리 15/100은 0.15 비율입니다. 조건은 `battery * 100f <= 15f`이므로 정확히 15%도 주황색입니다. `wasLow`는 이전 프레임 상태를 기억합니다. 현재 낮고 이전에는 낮지 않았을 때만 경고음을 재생하므로 매 프레임 처음부터 울리지 않습니다.

`wasUnderwater`도 같은 원리입니다. 지금 물속이고 직전에는 물속이 아니었다면 새 잠수가 시작된 것입니다. 이때 시간부터 0으로 만들고 `Time.deltaTime`을 더합니다. 다른 정보 패널도 `DiveSeconds`를 읽어 같은 잠수 시간을 사용합니다.

읽을 파일: `InformationManager.cs` → `DiveStatusHUD.cs` → `DiveInfo.cs`.

| 수신·상태 팝업 | IncomingCallPopup.cs | 실제 상태를 어떤 글자와 버튼으로 보여 줄까? |

“소리가 난다”는 사실만으로 통화 연결 여부를 정할 수 없습니다. 벨소리·연결음·목소리가 모두 소리이기 때문입니다. SimpleDial의 `CallState`를 먼저 읽으면 왜 여러 상태가 필요한지 이해할 수 있습니다. 상세한 실제 함수 흐름과 수신 반환값 문제는 `Calls_Setup_KO.md`에 설명했습니다.

## 8. 생물과 환경에서 읽을 파일

`CreatureSwim.cs`는 생물 root의 위치·회전을 움직입니다. 모델의 꼬리나 지느러미는 원본 수영 애니메이션이 움직입니다. 둘의 일을 나누고 애니메이션 루트 모션을 끄면, 경로 이동과 애니메이션이 같은 위치를 동시에 밀지 않습니다.

`ReefModel.cs`는 지정한 Resources 모델을 불러오고 준비한 재질을 연결합니다. `ClearWaterLook.cs`는 기본 수중 안개 색·밀도를 정합니다. 원본 MudStorm 자체를 지우거나 카메라 시야 제한을 끄는 역할을 맡기지 않았습니다.

`World_Setup_KO.md`에는 모델 정면축 보정, 실제 지형 높이 표본, 경로의 한계, 포함된 외부 자산 라이선스를 기록했습니다.

## 9. 버그를 찾을 때의 순서

버튼이 안 눌릴 때 바로 통화 코드를 고치기보다 입력부터 따라갑니다. 손이 추적되는가 → 버튼이 활성인가 → Collider가 UI 레이어에 있는가 → 레이가 그 버튼을 맞히는가 → 허용된 손인가 → 이번 프레임이 새 주먹 동작인가 → onClick이 의도한 함수를 가리키는가를 확인합니다. 어느 단계까지 관찰했는지를 적으면 수정 위치가 좁혀집니다.

오류를 재현할 때는 “안 된다” 대신 **어떤 상태에서, 어느 손으로, 어떤 버튼을, 어떤 방법으로 눌렀고, 화면·소리·이동에 무엇이 나타났는지** 기록합니다. Console 오류는 첫 번째 오류부터 확인합니다. 한 원인 때문에 뒤의 오류가 여러 개 생길 수 있기 때문입니다.

검사 종류도 구별합니다. C# 문법 검사로 문장 형식을 확인할 수 있고, 실제 소스를 실행한 논리 검사로 상태 변화를 확인할 수 있습니다. Unity의 Physics·Audio·XR을 대체한 검사에서는 실제 손 추적 정확도·양안 화면·청취 음량을 알 수 없습니다. 이 마지막 증거는 Quest로 얻습니다.

## 10. 시연을 끝낸 뒤 해 볼 작은 변경

별도 사본에서 `SimpleMovement`의 `speed`를 2.4에서 1.8로 바꾸고, 같은 손 동작을 했을 때 어떤 부분이 달라질지 먼저 적어 봅니다. `verticalSpeed`는 그대로일 때 합성 방향과 최고 속도 제한도 함께 생각합니다. Inspector에 이미 저장된 값과 C# 기본값은 다를 수 있으므로 실제 실행 값이 어디서 오는지도 확인합니다.

설명할 수 있어야 할 질문 하나: **“왼손으로 CALL을 고른 주먹이 전진 명령이 되지 않는 이유가 어느 파일 사이의 어떤 값에 있는가?”** 소스의 연결을 직접 찾아 설명하면 한 줄의 의미를 넘어 기능 전체를 이해했는지 확인할 수 있습니다. 이 연습은 발표 준비를 막는 필수 단계가 아닙니다.
